# Vibe Harness

一套可移植的 AI coding harness：用分层规则、专家技能、项目知识和变更证据，让 AI 编码过程更可控、更高效、更容易验证。

> 当前状态：公开预览版。核心结构与工作流已可使用，但仍需要在接入具体项目后补充项目事实、命令和质量门禁。

## 为什么使用 Vibe Harness

- **渐进式读取**：Agent 先读入口，再按任务加载一个主技能及必要规则，减少无关上下文。
- **规则与事实分层**：长期规范、可复用工作流、项目知识和单次变更证据各自维护，降低文档漂移。
- **闭环交付**：从需求分析、实现、测试、质量门禁、专家审查到发布验证都有明确入口。
- **证据优先**：代码、测试和可复现结果高于历史说明；未执行的验证不能写成已通过。
- **安全边界**：外部写入、付费服务、生产环境和高风险操作必须保留用户授权。

## 工作方式

```text
需求或缺陷
   ↓ request-analysis
结构化变更档案
   ↓ implement-change
代码与配套测试
   ↓ write-unit-tests / run-quality-gates
验证证据
   ↓ expert-review
独立风险审查
   ↓ deploy-verify（需要发布时）
可交付变更
```

## 快速开始

1. 将 `.harness/` 和根目录 `AGENTS.md` 复制到目标代码仓库。
2. 按真实项目填写 `.harness/wiki/` 中的六份上下文模板。
3. 按实际技术栈修改 `.harness/rules/`，删除不适用约束。
4. 把 `.harness/README.md` 中的测试、构建和运行命令替换为真实命令。
5. 运行自检：

```bash
python3 .harness/checks/check_harness.py
```

6. 从 `.harness/changes/_template/` 创建第一个变更档案，让 Agent 按任务路由执行。

## 目录

```text
.
├── AGENTS.md                 # Agent 总入口
└── .harness/
    ├── README.md             # 任务路由与使用约定
    ├── rules/                # 稳定、跨任务复用的工程约束
    ├── skills/               # 结构化专家工作流
    ├── wiki/                 # 项目事实与领域上下文模板
    ├── changes/              # 单次变更档案与验证证据
    └── checks/               # Harness 自检
```

## 内置专家技能

| 技能 | 用途 |
|---|---|
| `request-analysis` | 澄清需求、影响范围、验收标准和风险 |
| `implement-change` | 按已确认方案实现代码、测试和文档 |
| `write-unit-tests` | 设计高价值、确定性的回归测试 |
| `run-quality-gates` | 选择并执行与风险匹配的验证门禁 |
| `expert-review` | 独立审查正确性、架构、安全和可维护性 |
| `deploy-verify` | 准备部署前、部署中和部署后的分层验证 |

这些技能是仓库内的工作流事实源，不会自动安装到用户的全局 Codex 技能目录。

## 设计原则

- 不把全部仓库上下文一次性塞给 Agent。
- 不用 Prompt 替代可由代码执行的校验、权限或状态机。
- 不用历史变更档案替代长期规则和项目 Wiki。
- 不记录 Token、Cookie、内网地址、真实用户数据或完整生产日志。
- 不把“公开可见”等同于“获得开源许可证”。

## 适配说明

模板中的路径、语言、框架和命令都应以目标仓库为准。接入后建议：

- 在项目 Wiki 中指向真实代码、架构文档和事实源；
- 为关键规则建立静态检查或测试；
- 用小型真实变更校验整个工作流；
- 定期清理 `changes/` 中不应长期公开的运行证据。
