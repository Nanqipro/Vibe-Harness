# 工程结构规范

## 原则

- 先理解现有模块边界，再新增目录或抽象。
- 依赖方向从入口与编排层指向领域层、数据层和集成层，避免反向耦合。
- 单一事实源优先：注册表、配置、schema、Prompt 和展示映射不维护无必要副本。
- 新模块必须有清晰职责、调用方、测试位置和所有者。

## 通用分层

| 层 | 负责 | 不负责 |
|---|---|---|
| 入口/传输 | 解析请求、鉴权衔接、协议响应 | 复制领域或数据实现 |
| 领域/应用 | 业务规则、状态变化、用例编排 | 直接处理底层传输细节 |
| 数据访问 | 查询、持久化、事务封装 | 长流程业务决策 |
| 外部集成 | 鉴权、请求、响应校验、错误归一 | 用户话术或页面逻辑 |
| Agent/Prompt | 语义判断、工具编排、输出契约 | 替代确定性权限与校验 |
| 展示 | 渲染与交互 | 作为安全校验的唯一位置 |
| 测试 | 契约、边界、回归和不变量 | 依赖真实生产服务 |

## 扩展顺序

1. 搜索现有实现、测试和注册点。
2. 优先扩展职责相符的模块。
3. 只有现有边界无法承载时才新增模块，并记录证据。
4. 同步入口、配置、文档、测试和可观测性。
5. 通过依赖方向和重复实现检查。

避免创建 `helpers`、`common`、`misc`、`manager` 等缺少领域含义的垃圾桶目录。

## 边界检查

- 传输层与领域层之间使用明确输入/输出契约。
- 数据访问不返回无界结果，不把连接对象泄露到上层。
- 外部 client 不包含业务归因或用户话术。
- Prompt、工具 schema 和注册表变更必须有配套测试。
- 流式或异步流程覆盖开始、完成、错误、取消和恢复。
